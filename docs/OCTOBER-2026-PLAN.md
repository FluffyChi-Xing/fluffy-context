目标：为多人、多分支、多 agent 的真实协作保留可验证的项目状态和知识。10 月 16 日向公司活动提交介绍与技术报告；10 月 24 日前依据验收结果决定继续 beta、发布 RC 或发布 1.0，不以节日日期替代质量门槛。

## 10 月 14 日：beta.8 反馈修复与 beta.10 定义

- 范围：beta.8 ZCode 反馈对应的锁、runtime 启停、上下文相关性、日志索引、报告解释和短 ID 修复已提交。下一版定为 `1.0.0-beta.10`，跳过 beta.9；今天暂不发布 npm。
- 已有证据：180 项回归、pack 检查、tarball 全局安装逐文件校验和全局 CLI stop/start 冒烟在修复提交前已通过。beta.10 发布前须在最终候选上重跑。
- 证据边界：本机测试和 stdio 验收证明包与协议可用，不等于 ZCode 或 Codex 的自动触发、模型采用或效能收益。

## 下一版范围：1.0.0-beta.10

beta.10 是可靠性与真实接入的验收批，不扩大产品能力面。纳入已提交的 beta.8 ZCode 修复，并完成以下两项 P0 工作：

1. **runtime 并发与恢复**：用可复现的 Windows 压力夹具覆盖并发 start/stop、初始化时停止、慢日志写入、持有者异常退出、残留锁与再次拉起。每轮检查单活租约、最终可停止、可重启及日志全链完整；把失败环境和复现步骤留档。
2. **真实宿主连接**：ZCode 与 Codex 分别重连全局安装包，记录实际版本、任务开始/恢复/切换/错误/结束时的调用、返回模式和被最终输出采用的证据 ID。对宿主不支持的事件标记 unsupported。至少完成一条跨会话恢复和一条任务切换；能力声明和 MCP stdio 脚本不能代替宿主记录。

发布门槛：完成 P0 工作后将版本改为 beta.10，对最终候选运行全量测试、包内消费测试、`npm run install:local`、安装后 MCP stdio 验收和真实 runtime stop/start；无新增 P0 故障，并有上述真实宿主记录。通过后发布到 npm `beta` 标签，核对 registry 版本与 tarball；`latest` 保持 0.8.0。某一宿主无法完成时记录阻塞并明确缩小发布声明，不声称双宿主均已验收。

## 10 月 15–16 日：公司活动材料

1. **介绍文件**：用一个可复现的跨会话协作场景说明痛点、五个日常入口、候选与已验证知识的区别，以及 CLI/MCP 接入方式；给出安装命令、实际版本、平台要求和已知限制。
2. **技术报告**：说明事件日志与锁/租约恢复、按任务预算注入、来源指纹和知识状态、宿主 capability 与交付回执、固定任务评估设计。附实际使用版本的测试数、安装回执、MCP 调用记录、Git 提交和 tarball 校验值；区分本地包与 npm 公开包。
3. **现场演示**：在干净临时 Git 项目完成 init → checkpoint → 新会话 inject → learn/review → report；提前录制同流程的终端输出作为设备或网络故障备份。测试知识留在临时项目。

提交前核查：材料的版本、命令、截图和输出均来自实际安装包；若 beta.10 尚未发布，注明当前 npm beta.8 与未发布修复提交。把“已观察”“合成测试通过”“尚未验收”分列。只把当前 Windows 主机的测试结果称为本机验证；不提供未经测量的 token、时间或 ROI 改善数字。
